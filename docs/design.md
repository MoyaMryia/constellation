# Constellation OS 总体设计文档

版本：v0.1（草案）
日期：2026-08

## 1. 背景与命题

面向复古硬件的 Linux 移植（如 AOSC 星霞 OS）通常给出一个统一的最低内存需求
（星霞为 64 MiB），并注明该数字"以使用体验良好为基本基准"。但分析其架构
支持表可以发现：64 MiB 对 m68k（典型机型 4–32 MiB）、ARMv4（典型 32/64 MiB）、
早期 i486 机型（8–32 MiB）而言是多数真机够不到的门槛。

这个门槛的本质不是"这些架构需要 64 MiB"，而是"**那套软件栈**（现代内核 +
glibc + systemd + 桌面件）在任何架构上都需要约 64 MiB 才算好用"。

Constellation OS 的命题由此而来：

> **把"软件栈版本"和"资源占用"解耦。在旧机器的硬件约束内，每个组件都选用
> 能达到的最高上游版本；压低下限靠的是选型，而不是冻结版本。**

## 2. 目标硬件与分档

### 2.1 参考机型

IBM ThinkPad 365X / 365XD：

- CPU：Pentium 133 MHz，无 MMX（i586，含 FPU、TSC、CPUID）
- 内存：板载 8 MiB + 扩展槽，实机配置 24 MiB / 40 MiB 两档
- 存储：IDE 硬盘，约 810 MiB–1.3 GiB
- 外设：16 位 PCMCIA（有线网卡）、软驱、无 USB 或仅 USB 1.0
- 显示：800×600 DSTN/TFT，VGA 兼容

### 2.2 二进制基线：i486

软件包统一以 **i486** 为基线指令集编译：

- 覆盖区间最大：真 486 → Pentium（无 MMX）→ 之后的全部 x86 均可运行。
- i486 与 i586 基线在常规负载下性能差距很小（i586 主要多 TSC/CX8 等指令的
  使用，用户空间收益有限），不值得为参考机型单独开一档。
- 编译器目标名：`i486-constellation-linux-musl`（工具链）；
  软件包架构名：`i486`。
- 内核侧注意：上游 7.x 已移除真 486 的 CPU 支持，真 486 机型须使用
  `linux-legacy486` 内核风味（§3.2）；Pentium 及以上不受影响。

### 2.3 内存分档

| 档位 | 内存 | 形态 | 预期体验 |
|---|---|---|---|
| **T0 基础档** | 24 MiB | 纯命令行 | shell、文本编辑、串口/有线网络、包管理可用；编译不在本机进行 |
| **T1 扩展档** | 40 MiB | 命令行 + 轻量图形 | 在 T0 基础上可运行帧缓冲图形应用（看图、fbi/links -g），可探索极简 X |
| T2（未来） | ≥64 MiB | 图形桌面 | 非首发目标，仅作为对比锚点 |

每档单独出具实测需求表，**不写"全项目统一最低配置"**——这是从星霞需求表
失真问题直接继承的设计原则。

## 3. 软件栈选型

总原则：每个组件按"满足主流维护与旧机协调的最高版本（§5 的基准标准）→
实测内存占用 → 是否挤爆预算"的顺序决策；装不下时先换同版本轻量实现，
再考虑降版本，最后才砍功能。所有降级在 §7 的决策日志中留痕。

### 3.1 选型总表

| 组件 | 选型 | 版本策略 | 理由 |
|---|---|---|---|
| 内核 | Linux，最新 **LTS** 系列，定制精简配置 | 跟随最新 LTS | 版本新与体积小的主要杠杆在 .config，不在版本号 |
| libc | **musl** | 最新稳定版 | 静态开销远低于 glibc；静态链接工具链体积小 |
| 核心工具 | **BusyBox** | 最新稳定版 | 一个二进制替代 coreutils/util-linux 大部分功能 |
| init / 服务管理 | **s6** + s6-rc（备选 runit） | 最新稳定版 | systemd 在这档内存上不可行；s6/runit 常驻开销 < 1 MiB |
| shell | BusyBox ash（可选 mksh） | 最新 | ash 够用；mksh 留给交互体验更好的一档 |
| 包管理器 | **apk**（Alpine 格式，v3） | 最新稳定版 | C 实现、依赖解析快、内存占用小；格式成熟有现成生态参考 |
| TLS | **mbed TLS**（首选）/ LibreSSL（备选） | 最新稳定版 | OpenSSL 3.x 体积与内存占用在这档预算下偏大 |
| 网络 | 有线为主：BusyBox udhcpc + 内核驱动 | — | PCMCIA 有线网卡是参考机型现实路径；Wi-Fi 非首发 |
| 图形（T1） | Linux 帧缓冲 + fb 系应用 | — | 见 §3.3 |
| 编译器 | GCC（C/C++），交叉编译 | 最新稳定版 | 本机不编译；宿主机交叉产出 i486-musl 工具链 |

### 3.2 内核策略

- 跟随"主流维护中"的最高 LTS（§5 基准标准），**版本一行不动，内存全靠
  裁 .config**——这是 Constellation 内核策略的核心：上游的体积增长发生在
  默认配置与驱动生态里，而不在我们需要的代码路径上。
- **裁剪目标**（M1 验收标准，实测回填）：
  - bzImage（XZ 压缩）≤ 2.5 MiB；
  - 启动后内核常驻（`/proc/meminfo` 基线，含页表/驱动）≤ 8 MiB @ 24 MiB 机型。
- **裁剪清单**（按收益从大到小）：
  - 只保留参考机型硬件：IDE/libata、16 位 PCMCIA、NE2000 兼容网卡、
    VGA 帧缓冲——**启动必需驱动全内置，非启动必需驱动编成模块**
    （`CONFIG_MODULES` + `CONFIG_MODULE_UNLOAD`）。内置：`ATA_PIIX`、
    `BLK_DEV_SD`、`EXT4_FS`；模块：PCMCIA 栈、8390 网卡、VGA16 fb 等。
    模块基础设施成本已量化：约 144 K 用户态可用内存 + 52 KiB bzImage
    （kernel/NOTES.md），在 24 MiB 预算内可接受，换来用户可
    `insmod`/`modprobe` 额外驱动；
  - 文件系统只留 ext4 + proc/sysfs/tmpfs（initrd 以外一切可裁）；
  - 关调试全家桶：SLUB debug、KASAN、kprobes/ftrace/perf、eBPF 大半、
    内核态 Rust（若该 LTS 含）；
  - 关声音栈（T0）、关 DRM/KMS（用 vesafb/简单 fb）、关 USB（参考机型
    无或仅 1.0，非首发）、关 cgroup v2 非必要控制器、关 namespaces 非必要项
    （需与 s6 需求核对）；
  - 网络栈保留 IPv4 + 基础 netfilter，裁 NF_CONNTRACK 非必要 helper、
    关 IPv6（可议，见 D9）；
  - 安全特性权衡：保留基础 hardening（STACKPROTECTOR、FORTIFY），
    按需评估高位开销项（如 IBT/页表隔离类在 i586 上本就不适用）。
  - 压缩：内核镜像 XZ；运行期交换优先 zram（LZ4），后备写回 IDE swap。
- **裁剪配置的维护成本极低**：老硬件的驱动需求是冻结的，每次跨 LTS 迁移
  .config 只做一次 `oldconfig` 差异审查——这与 §5 长周期 LTS 模型咬合：
  几年才迁一次。
- **vintage 选择：已定 6.18 LTS**（2026-08 核实 kernel.org）：

  | LTS | 预计 EOL | 状态 |
  |---|---|---|
  | 5.10 / 5.15 | 2026-12 | 即将 EOL，排除 |
  | 6.1 / 6.6 | 2027-12 | 已做 L0/L1 对比后移除 |
  | 6.12 / 6.18 | 2028-12 | **选用 6.18**，上游覆盖最长 |

  权衡要点：Constellation 自身 LTS 周期 3–5 年，**任何上游 LTS 都会在
  周期中段 EOL**，自维护不可避免。M1 裁剪实验 L0/L1 已回填：6.1 比
  6.18 多 420 K（L0）/ 468 K（L1）用户态内存，均低于 2 MiB 阈值；
  按"上游覆盖最长"原则选定 **6.18.44**，6.1 配置已从仓库移除。
  5.x/6.x 全系仍含 `M486`——真 486 由 `linux-legacy486` 风味承接。
- **EOL 接力链（内核）**：内核 EOL 是预期事件（任何 vintage 都会在我们
  3–5 年周期中段 EOL），按以下顺序接力：
  1. **扩展维护生态**：CIP SLTS（如 6.1-cip 维护至 ~2033）、发行版长期
     维护树（Debian ELTS 等）——任一存活即视为"主流维护中"（§5），
     直接跟踪其树；
  2. **自维护**（§3.5 阶段 b）：冻结版本，自行回填安全修复。内核在此
     有两个独特优势：(a) **猛裁配置 = 攻击面已削减**，多数上游修复/CVE
     落在被整个编掉的子系统（DRM、声音、eBPF、非常用文件系统等），
     分诊后多为"不适用"，实际移植量远小于全配置内核；(b) 构建链由
     我们的可复现构建系统钉死，§3.5 的"构建链断裂"撤退条件对内核
     几乎不触发；
  3. **撤退**：按 §3.5 章程执行（冻结最后版本、镜像永存、文档留档）。
  另注：复古机威胁模型（单用户、常在 NAT 后或离线）决定其风险容忍度
  不同于服务器，自维护期的修复优先级排序可据此调整。
- **已确认：上游已移除 i486 支持**（2026-08 核实）。主线（7.x 开发树，
  用户报告的 7.1 与之一致）`arch/x86/Kconfig.cpu` 中 `M486` 已删除，
  最低档为 `M586TSC`（Pentium Classic）；6.x 全系（实测至 6.18 stable）
  仍保留 `M486`。即：**最后支持真 486 的内核线是 6.x，6.18 是其中最晚的
  稳定/LTS 分支**。
- **应对：双内核风味**（按 §5 基准标准与 §3.5 生命周期的自然推论）：
  - `linux`（默认风味）：跟随"主流维护中"的最高 LTS（7.x 起），
    Pentium 及以上机型使用——参考机型 ThinkPad 365X/XD 走这条路，
    完全不受上游移除影响；
  - `linux-legacy486`：钉在 6.18 LTS，进入 §3.5 自维护期语义（自行合入
    安全修复直至撤退条件触发），仅面向真 486 机型。该风味套用同一份
    裁剪清单与验收目标，且不影响主线的版本就高。
  - 注意区分两层：**用户空间 i486 二进制基线**是编译器目标问题（GCC 仍
    支持，不受内核移除影响）；**内核 CPU 支持**才是本次移除的对象。
    Pentium+ 机型两者皆无影响。
- FPU 注意：486SX 无 FPU，需要内核数学模拟（CONFIG_MATH_EMULATION，
  其当前上游状态待核实）；参考机型 Pentium 自带 FPU，不受此约束。

### 3.3 图形栈（T1 档，40 MiB）

按内存从低到高的候选顺序：

1. **纯帧缓冲应用**：fbi（看图）、links2 -g（图形浏览器）、cairo-fb 小程序。
   无显示服务器开销，最稳。
2. **极简 X**：kdrive/TinyX 系（Xfbdev 已在 xorg-server 21.1 移除，若走此路
   需自维护旧分支或采用 TinyX 衍生项目，状态待核实）+ 微型 WM
   （如 tinywm/flwm）。历史经验 X + twm 级会话可在 ~20 MiB 用户空间内运行，
   但留给应用的余量很小。
3. 完整 Xorg + fbdev 驱动：预计常驻占用偏大，T1 档可能紧张，列为实验项。

浏览器现实上限：links2（图形模式）是 T1 的甜点；NetSurf-fb 内存需求
（~30 MiB+）预计超出 T1 预算，留作 T2 评估。

### 3.5 支持生命周期策略：尽力支持，力竭则撤

Constellation 对硬件/架构的支持**不设预设期限、不主动缩圈**。每一项支持
（如 i486 基线、某档内存、某个外设栈）遵循如下生命周期：

1. **跟随期**：上游支持什么，我们跟到什么。默认状态。
2. **自维护期**：上游放弃后（如内核移除某 CPU 支持、工具链移除某目标），
   依次尝试：(a) 背负 revert/移植补丁继续跟新版；(b) 停留在上游放弃的
   最后一个 LTS 并自行合入安全修复。只要成本可承受，就一直维持。
3. **撤退期**：当满足撤退条件（见下）时，按章程撤退，不搞突然死亡：
   - 冻结最后一个可用版本，镜像与仓库永久保留可下载；
   - 文档明确标注"已终止支持"及最后可用版本号；
   - 需求表中将该档位/架构移至"历史支持"一节，而非删除——留下完整记录。

**撤退条件**（满足其一即启动评估，由维护者在决策日志中书面确认）：

- 自维护补丁连续两个上游 LTS 周期无法以合理人力完成移植/冲突解决；
- 构建链断裂（如 GCC/binutils 移除目标且无可行替代编译器）；
- 无可用验证环境：既没有真机，模拟器也无法再复现目标配置。

这一策略直接适用于 D1（内核 i486 移除）：**默认进入自维护期(a)，即背负
补丁继续跟新 LTS；跟不动再退 (b)；(b) 也守不住才撤**。

## 4. 构建与分发

- **交叉构建**：宿主机（现代 x86_64）上构建 `i486-constellation-linux-musl`
  交叉工具链（binutils + GCC + musl），全部软件包交叉编译。
  本机编译明确不支持（24 MiB + Pentium 133 上跑 GCC 不现实）。
- **构建系统**：自维护 Makefile/脚本驱动的包配方集合（buildroot 风格但独立，
  便于控制每个包的裁剪项）；每个配方记录上游版本号与裁剪理由。
- **软件包**：apk v3 格式，按档位分仓库（t0/t1），包粒度细
  （如 busybox 各 applet 不拆，但网络/图形组件独立成包）。
- **镜像生成**：`mkimage` 脚本从 apk 仓库确定性生成磁盘镜像
  （分区/格式化用固定时间戳等确定性参数 → `apk --root` 装包 →
  extlinux/syslinux 引导器）——同一仓库快照产出逐位一致的镜像，
  这也是 §5 归档策略"镜像 = 脚本产物"的实现基础；
- **安装形态**：
  - 首发：在 Linux 下把生成的磁盘镜像写入目标盘，通过软盘或
    PCMCIA 网卡把镜像送进目标机；
  - 目标机原生安装程序（24 MiB 内存下可运行的文本安装器）列为里程碑 M4。

## 5. 发布模型：现代基准 + 长周期大 LTS

Constellation 不跟随滚动更新，采用**长周期 LTS 类模型**：

- **定基准**：每个大版本锁定一个"现代基准"。基准的选择标准**不是"最新"**，
  而是按优先级取同时满足下列条件的最高版本：
  1. **主流可用**：仍获上游或主流生态维护（安全修复可持续获得、有现成
     补丁生态），不选已 EOL 的版本；
  2. **协调旧机**：在目标硬件上实测协调——支持 i486 基线、内存占用符合
     预算（docs/memory-budget.md）、慢 CPU 上性能可接受；
  3. 在前两条约束内**尽量新**。

  即：基准完全可以是"仍受维护的次新 LTS"，而非"刚发布的最新版"——若最新
  上游移除了旧硬件支持或实测在 24 MiB 下退化，就选择仍协调旧机的最高维护
  中版本，差额由 §3.5 的自维护期机制兜底。基准一经锁定，本周期内不再追新。
  "主流维护中"的认定范围包括：上游官方维护、CIP SLTS 等扩展维护项目、
  主流发行版的长期维护树（如 Debian ELTS）——任一存活即算数。
- **长间隔**：大版本间隔以**数年**计（目标 3–5 年，实际以"新版本带来的
  收益是否值得老机器用户重装/大升级"为判据）。间隔期内不引入版本升级，
  只回填修复——回填范围按 §5.1 的安全姿态分诊，不做服务器级 SLA 承诺。

### 5.1 安全姿态

Constellation 的威胁模型：**单用户、爱好者机器、常离线或位于 NAT 后**。
定向攻击概率趋零（为 i486-musl 异类目标写 exploit 无投入产出）；
残余风险来自自动化扫描/蠕虫与老协议实现漏洞。据此：

- **防御靠架构，不靠补丁 SLA**：极简攻击面（猛裁的内核配置、少量
  软件包）+ 目标异类性（32 位 i486-musl 使绝大多数现成 exploit 哑火）
  + **默认无暴露面**（默认不监听任何端口、无默认账户、SSH 取代
  telnet）；
- **安全修复按分诊回填**：仅回填"在本威胁模型下实际可利用"的高危
  修复（如默认安装的监听服务、协议解析漏洞）；落在已裁减子系统、
  本地提权类（单用户无意义）等情形的修复**不追**，随下一 LTS 自然
  解决——这是对维护者的诚实减负，与 §3.5"尽力支持"不矛盾：
  尽力的方向是把系统造对，不是把补丁追全；
- **文档如实告知**：发布说明中明确此姿态，建议用户勿将本系统用作
  公网服务器或处理敏感数据。
- **为什么这个模型特别适合复古硬件**：
  1. 老机器的升级成本高（慢 CPU 解包、小磁盘、无高速网络），频繁更新是
     负担而非福利；
  2. 硬件本身不再变化——驱动需求是冻结的，追新的边际收益远低于现代机器；
  3. 维护者精力集中在每几年一次的基准重估上，平时维护负担小，与 §3.5
     "尽力支持"的自维护期天然兼容：LTS 周期长 = 自维护的负担被摊薄。
- **与 §3.5 生命周期的衔接**：每个 LTS 在其整个周期内享受完整支持；下一
  LTS 发布后，旧 LTS 进入自维护期语义（安全修复再维持一个重叠期，目标
  ≥1 年），随后按撤退章程归档为"历史版本"，镜像永久保留。
- **版本号**：`1.x.y` 形式，**版本号 = 对升级路径的承诺**：
  - **大版本号**：**当无法保证"全部受支持硬件都能从包原地升级"时升**
    （1 → 2）。两类触发情形：(a) 用户空间 ABI 断裂类；(b) **硬件支持
    矩阵变化使部分机器拉包升级会变砖**——例：基准迁到 7.x 内核后，
    486 机器 `apk upgrade` 会拉到无法引导的 `linux` 包，故该迁移必须
    升大版本（届时 486 用户留在 1.x 线，由 §3.5 生命周期继续承接）。
    设计目标是它几乎不发生；但触发条件满足时**必须升**——承诺不可
    违背；
  - **中版本号（x）**：LTS 基准更替 +1（1.0、1.1、1.2 …），无上限。
    **发布验收条件：上一线的全部受支持硬件配置均可 `apk` 原地升级**
    （用户自行拉包更新，不重装、不变砖）——升级路径测试覆盖整个
    硬件支持矩阵，列入 LTS 发布检查单；
  - **小版本号（y）**：线内维护更新，常规 `apk update && apk upgrade`；
  - 设计意图：用户看到中版本号变化即知"拉包即可"，看到大版本号
    变化即知"升级路径不再保证，按发布说明操作"。为守住中版本号
    承诺，LTS 更替须保持 ABI 兼容（soname 钉定等）与硬件支持矩阵
    稳定；两者之一守不住时，正是大版本号该动之时——罕见但有意义。
- **归档策略**：轻量两件套——**git 提交记录 + 每条 LTS 线（1.x）的
  最终镜像**：
  - **git 仓库即档案**：构建配方、裁剪 .config、文档、决策日志的全部
    历史天然留痕；配方中钉死每个软件包的上游版本号与校验和，任意
    历史提交可重建对应系统状态（线内小版本无需单独归档）；
  - **每线最终二进制仓库快照**（体积仅数百 MB 级）：线终结（含撤退）
    时冻结 `1.x` 最终维护版本的完整 apk 仓库，永久可下载——归档系统
    日后仍可装包，而不只是"装好什么用什么"；
  - **镜像 = 脚本的产物**：git 内置 `mkimage` 脚本，从二进制仓库快照
    **确定性生成**最终安装镜像（创建磁盘镜像 → 分区/格式化（固定
    时间戳等确定性参数）→ `apk --root` 装包 → 写引导器）。权威归档
    是"脚本 + 仓库快照"，预生成镜像仅作为便利缓存提供，丢失可用
    脚本原地重建——"能跑"的最终证据因此不依赖任何单一存档物；
  - **已知取舍**：不存档上游源码包快照，离线重建能力依赖上游/镜像站
    源码仍可获取（配方内的校验和保证"拿到的就是对的那一份"；
    Software Heritage 等公共存档作兜底）。若某源码永久失联：已冻结
    镜像与仓库的可用性**不受影响**，仅该包失去重建能力，于该线
    "支持档案"中注明；
  - 每线归档附"支持档案"（git 内文档）：硬件分档需求表、已知问题、
    撤退原因（若适用）——十年后翻出机器的人可装、可查，（源码在线时）
    可建。这正是 §3.5 撤退章程的落地形态。

## 6. 与星霞 OS 的对照



| 维度 | 星霞 OS (Afterglow) | Constellation OS |
|---|---|---|
| 目标 | 多架构复古移植，体验良好基准 | 单架构（x86）起步，内存下限优先 |
| 最低内存 | 64 MiB（统一表） | 24 MiB（T0，分档表） |
| libc | glibc | musl |
| init | systemd 系 | s6 / runit |
| 核心工具 | GNU coreutils | BusyBox |
| 版本策略 | 现代栈 | 现代栈（每个 LTS 锁定"主流维护中且协调旧机"的最高版本） |
| 发布模型 | 滚动更新 | 长周期大 LTS（3–5 年），周期间只回填修复 |
| 代价 | 内存地板高 | 功能面窄（无 systemd 生态、glibc 兼容性弱） |

关键论点：**两者软件栈版本处于同一时代，内存地板相差约 2.5 倍**。差值全部
来自选型，这正是 Constellation 命题的实证。

## 7. 决策日志与开放问题

| 编号 | 事项 | 状态 |
|---|---|---|
| D1 | 内核 i486 移除后的策略 | **已核实**（2026-08）：主线 7.x 已删 `M486`，6.18 为最后支持的稳定线。**已定**：双内核风味——默认 `linux` 跟随最高维护中 LTS（Pentium+），`linux-legacy486` 钉 6.18 LTS 进入自维护期（真 486 专用）。执行细节：M1 时验证 6.18 在 24 MiB 下的可裁剪性 |
| D2 | s6 还是 runit（s6-rc 表达力强，runit 更简单） | 原型阶段实测对比 |
| D3 | apk 自举路径（静态 apk + 最小仓库先行） | 待原型 |
| D4 | T1 图形走 fb 直连还是 TinyX | 需实机/86Box 实测内存 |
| D5 | CONFIG_MATH_EMULATION 上游现状（影响 486SX 覆盖） | 待核实 |
| D6 | 是否引入 Rust/Go 等现代语言包（其 i586/i486 目标可用性、体积） | 非首发，待评估 |
| D7 | 是否增设 TX 极限档（16 MiB，CLI-only，重度 swap） | M1/M2 实测 16 MiB 可用性后决策，见 memory-budget.md §3.1 |
| D8 | LTS 间隔具体定几年（3–5 年的判据：新版收益是否值得老机器重装） | 首个 LTS 发布后根据维护实况校准 |
| D9 | 内核是否裁掉 IPv6（省内存与镜像体积 vs 现代网络环境的可达性） | M1 裁剪实验时评估：量化 IPv6 的常驻开销后再定 |
| D10 | 首个 LTS 的内核 vintage：6.18（上游覆盖最长）vs 6.1/6.6（体积更小但早进自维护） | **已定（2026-08）：6.18.44**。6.1 对比数据：L0 多 420 K / L1 多 468 K 用户态内存，均低于 2 MiB 阈值；6.1 配置已移除，仓库只保留 6.18。数据见 kernel/NOTES.md |
| D11 | 目标系统是否需要包管理器 | **已定：保留 apk**。常驻内存为零（非守护进程，仅操作期峰值 2–3 MiB），磁盘成本 ~数 MB；换回：用户改装权、周期内按包投递安全修复（慢网慢盘下数量级地便宜于整刷镜像）、与 §5 归档流水线自洽。约束：基础系统必须自洽完整——从不碰 apk 也能完整使用，包管理器是增益不是依赖 |

验证环境：86Box（精确模拟 Pentium 133 + 24/40 MiB）为主要 CI 目标，
QEMU（-cpu 486/pentium, -m 24/40）为快速回归环境，最终真机确认。

## 8. 路线图

- **M0 工具链**：交叉工具链 + Hello World 静态二进制在 86Box 目标上运行。
- **M1 可引导核心**：精简 LTS 内核 + BusyBox initramfs，24 MiB 内存启动到 shell。
  **已跑通**（2026-08）：6.18.44 + musl i486 静态 BusyBox 1.38.0，
  QEMU `-cpu pentium -m 24` 落到 ash；L1 内核层（IDE/libata/ext4 + DOS 分区）
  已 QEMU 验证；**syslinux 引导链已跑通**：BIOS → MBR → SYSLINUX → bzImage
  → ext4 root → BusyBox PID 1（见 kernel/NOTES.md）。
  **L2 外设已开工（2026-08，仅 6.18.44）**：`PCCARD`/`PCMCIA`/`I82365`、
  8390 家族（`NE2000`/`NE2K_PCI`/`PCMCIA_PCNET`）、`FB`/`FB_VESA`/
  `FB_VGA16` 已编入；**非启动必需驱动已改为 `m`**，QEMU 下 `insmod`
  ne2k-pci 后识别 `eth0`；fb 实绑待 86Box/VESA 路径。
  **L3 内存机制已跑通**：`ZRAM=y` + `ZRAM_BACKEND_LZ4=y` +
  `ZRAM_DEF_COMP_LZ4=y`；QEMU 下 `mkswap /dev/zram0` + `swapon /dev/zram0`
  成功，`free` 显示 8 MiB zram swap 可用。
- **M2 最小系统**：musl + s6 + apk + 基础仓库（~30 包），硬盘安装形态可用，
  出 T0 实测需求表。
- **M3 网络与包生态**：PCMCIA 有线网络、udhcpc、远程 apk 仓库，包数 ~100。
- **M4 安装器**：24 MiB 可运行的文本安装程序。
- **M5 T1 图形档**：fb 应用集，出 T1 实测需求表。
