# x86_64 / ThinkPad X61 风味（分支 `x61-amd64`）

本文档记录 Constellation OS 的 **x86_64 风味**：面向 ThinkPad X61
（T7100 / GM965+ICH8M / GMA X3100 / Intel 82566MM / 8GB DDR2 / 90GB SSD），
64 位用户空间，内存下限以实测为准（不预设）。

## 1. 结论先行

| 项目 | 结果 |
|---|---|
| 内核 | Linux 6.18.44（最新 LTS），bzImage **1.95 MiB** |
| 用户空间 | musl 1.2.5 + BusyBox 1.38.0（**466 KiB**，109 applet）+ s6 2.15.1.0 |
| 包管理 | apk-tools 3.0.7（v3 格式，静态，816 KiB） |
| 引导链 | BIOS → MBR/GRUB → bzImage → ext4 root → s6-svscan → getty |
| **内存下限（全功能）** | **29 MiB**（28 MiB 时内核解压阶段即失败，串口零输出） |
| 30 MiB 时启动后空闲 | 约 16 MiB（`MemFree` 基线见 §5） |

对照：i486 线的 T0 目标是 24 MiB。**64 位地板更高是符合预期的**（指针/结构体
变大、页表更大）——本分支为设计文档 D7（是否增设极限档）提供了 x86_64 侧的
实测数据点。

## 2. 与 i486 线的差异

1. **32 位 → 64 位**：用户空间基线由 i486 改为 x86_64；内核配置须在
   x86_64 的 Kconfig 树上重新表达（不能直接复用 L4 的 i386 .config）。
2. **硬件换了一代**：ICH8M SATA（`SATA_AHCI`）取代 PATA 为必需；Intel
   82566MM（`E1000E`）取代 8390/PCMCIA；GMA X3100 走 VBE 帧缓冲。
3. **`CONFIG_MODULES=n`**：X61 所需驱动全部内置，省下模块基础设施开销
   （i486 线量化为约 144 K 内存 + 52 KiB 镜像）。
4. **多一个网络服务**：`/etc/s6/udhcpc` 把 e1000e 拉起来并取租约（对应
   i486 线的 M3 内容，此处提前落地以完成验收）。
5. **双 getty**：`getty-console`（tty1，X61 本地屏）与 `getty-serial`
   （ttyS0，QEMU 验收通道）；各自在对应 tty 不存在时退到 sleep，不刷日志。

## 3. 构建（在 x86_64 Linux 宿主上，全程免 root）

依赖：`gcc make curl tar xz bzip2 cpio pkg-config python3 meson(meson>=0.64，
脚本用 pip 装到 build/pip-meson-amd64) sfdisk mtools e2fsprogs grub-pc-bin`。

```sh
JOBS=16 scripts/build-core-amd64.sh       # musl x86_64 + 内核头 + bzImage + BusyBox
JOBS=16 scripts/build-s6-amd64.sh         # skalibs/execline/s6（静态）
JOBS=16 scripts/build-crossdeps-amd64.sh  # zlib + mbedTLS（apk 的依赖）
JOBS=16 scripts/build-apk-amd64.sh        # apk-tools 3.0.7（静态）
        scripts/mkrepo-amd64.sh           # 自建示例仓库（验收 apk 用）
ROOT_PASSWORD_HASH="$(openssl passwd -6 '你的密码')" \
  APK_DEMO_REPO=$PWD/build/apk-repo-amd64 \
  scripts/build-rootfs-amd64.sh           # 组装 rootfs
        scripts/mkimage-amd64.sh          # 产出可引导镜像（512 MiB）
        scripts/memsweep-amd64.sh         # 内存下限扫描
```

产物：`build/amd64/constellation-x61.img`。

## 4. 验收（QEMU 近似 X61 档）

QEMU 无 ICH8M/965GM 的精确模型，用最接近的组合代替：
`-machine q35 -cpu core2duo -device ich9-ahci -device e1000e -vga std`。

四条验收**全部通过**，且是在**真实引导链**（BIOS→GRUB→内核，非 `-kernel`）下
逐条登入确认的：

| 验收项 | 证据 |
|---|---|
| 到 shell + getty 登录 | `constellation login:`；`root` 登录成功；`uname -a` → `Linux constellation 6.18.44 … x86_64` |
| 有线网通（e1000e + DHCP） | `e1000e … eth0: NIC Link is Up 1000 Mbps`；`udhcpc: lease of 10.0.2.15`；`inet 10.0.2.15/24` |
| 图形控制台（vesafb 1024x768） | `vesafb: mode is 1024x768x16`；`fb0: VESA VGA`；`/proc/fb` → `0 VESA VGA`；`Console: switching to colour frame buffer device 128x48` |
| zram swap + apk 可用 | `zram0 swap on (16777216 bytes)`，`/proc/swaps` 有 zram0；`apk --version` → 3.0.7；`apk add … constellation-release` 安装成功且文件落地 |

## 5. 内存下限实测

`scripts/memsweep-amd64.sh`，每档引导到"全绿"或超时。判定列含义见脚本头注释。

| -m (MiB) | kernel | init | login | net | zram | 内核可见内存 |
|---|---|---|---|---|---|---|
| 128 | yes | yes | yes | yes | yes | 113 MB / 126 MB |
| 64 | yes | yes | yes | yes | yes | 51164K / 65012K |
| 32 | yes | yes | yes | yes | yes | 18420K / 32244K |
| **29** | **yes** | **yes** | **yes** | **yes** | **yes** | **15368K / 29172K** |
| 28 | no | no | no | no | no | —（0 字节串口输出） |

- **地板 = 29 MiB**；30 MiB 时空闲约 16 MiB，说明系统本身（内核+用户空间
  常驻）约耗 14 MiB。
- 28→29 之间是断崖式失败：28 MiB 时**一个字节的串口输出都没有**，即内核
  解压/早期初始化阶段就没过去，而不是某个服务起不来。
- 该断崖由内核自身的最小内存需求决定（本配置下 `Memory:` 行显示内核在进入
  用户空间前已占用约 13.8 MiB）。

## 6. 踩坑清单（症状 → 原因 → 修法）

这些是本次落地中真实拦住过进度的点，后续写 32 位线或迁移配置时会再遇到。

### 6.1 内核配置

| 症状 | 原因 | 修法 |
|---|---|---|
| tinyconfig 里 `CONFIG_NETDEVICES` 为 n，导致 `E1000E`、`NET_VENDOR_INTEL` 全都不可见（`--enable` 写入后被 olddefconfig 丢弃） | `drivers/net` 整棵树挂在 `menuconfig NETDEVICES` 之下 | fragment 里显式 `CONFIG_NETDEVICES=y` 与 `CONFIG_NET_VENDOR_INTEL=y` |
| 同样地 `E1000E` 依赖 `PTP_1588_CLOCK_OPTIONAL` | tinyconfig 关掉了该"可选依赖"符号 | fragment 里显式开启 |
| `Starting init: /sbin/init exists but couldn't execute it (error -8)`（ENOEXEC），系统回退到 `/bin/sh` 当 init | tinyconfig 未开 `CONFIG_BINFMT_SCRIPT`，内核不认识 `#!` | fragment 加 `CONFIG_BINFMT_SCRIPT=y` |
| s6-svscan 报"another instance … already running" | 缺 `CONFIG_FILE_LOCKING`（i486 线 M2 笔记也记过同一个坑） | fragment 加 `CONFIG_FILE_LOCKING=y` |
| 关掉 `CONFIG_EXPERT` 后 bzImage 反而从 1.90 MiB 涨到 2.40 MiB | EXPERT 是"允许关掉各种默认 y"的闸门；关掉它后 `KALLSYMS`/`NAMESPACES`/`COREDUMP` 被强制默认打开 | **保持 EXPERT=y**，逐项显式关掉真正占内存的符号；`DEBUG_KERNEL` 因 EXPERT 的 `select` 无法关闭，但它只是门控、不产生代码 |

### 6.2 用户空间

| 症状 | 原因 | 修法 |
|---|---|---|
| `/sbin/init` 执行了但立刻掉进 shell，主机名是 `(none)`、`root` 被当命令执行 | 内核开了 `CONFIG_DEVTMPFS_MOUNT`，`/dev` 已被自动挂载，init 里 `mount … /dev` 拿到 EBUSY，被 `\|\| exec sh` 误判为失败 | init 改为幂等：先尝试挂载（忽略错误），再用 `/proc/mounts` 复核，只有真的没挂上才回退 |
| 所有 getty 没有登录提示符，`run` 脚本报 `[: not found` | BusyBox 的 M1 配置没有 ash 内建 `[`（选项名是 `ASH_TEST`，不是 `ASH_BUILTIN_TEST`） | 开 `CONFIG_ASH_TEST/ECHO/PRINTF`；另注意**不要**给 `[` 建软链（BusyBox applet 表里没有该名字，会 "applet not found"） |
| `busybox --list` / `--install` 报 "applet not found" | 元 applet `CONFIG_BUSYBOX` 未开 | fragment 加 `CONFIG_BUSYBOX=y` |
| BusyBox fragment 里新 applet 全部被丢弃，日志报 `trying to reassign symbol CP` | 直接追加 `CONFIG_X=y` 与基线里既有的 `# CONFIG_X is not set` 重复，Kconfig 取先出现的那条 | 先 `sed` 删掉 fragment 涉及符号的既有条目，再追加，最后 `olddefconfig` |
| `head -3` / `tail -8` 报 "unrecognized option" | BusyBox 的 head/tail 只认 `-n N` | 用 `-n` 写法（或习惯性避免省略形式） |
| apk 调用 BusyBox wget 时段错误（`wget[90]: segfault at 0`） | BusyBox wget 在 apk 传入的参数形态下崩溃 | 用 apk 内置 libfetch（但 libfetch 需要 openssl 头）或走本地仓库；本地仓库路径不经抓取层 |

### 6.3 构建与制盘

| 症状 | 原因 | 修法 |
|---|---|---|
| `make O=… ARCH=x86_64` 报 "The source tree is not clean" | i486 线的构建产物就在 `kernel/src/linux-6.18` 里，O= 分离构建要求源树干净 | x86_64 线从原始 tarball 解到 `build/amd64/`，不动 i486 的树 |
| musl 交叉构建报 `x86_64-linux-musl-ar: No such file` | musl Makefile 按 `--target` 推导工具前缀 | configure 时显式传 `AR=ar RANLIB=ranlib` |
| skarnet.org 不可达（SSL 直接 EOF） | 本机网络到该站被断 | `build-s6-amd64.sh` 做双源回退：skarnet 官方 → NJU 的 Debian pool；两个来源的 SHA256 都钉进契约 |
| `grub-bios-setup` 报 "disk does not exist, falling back to /dev/nvme0n1p2" | 它只接受真实块设备（"DEVICE must be an OS device"），对普通文件会去猜宿主根设备 | 改用 GRUB 手工布局：`cat boot.img core.img > 头`，再把分区表 66 字节（偏移 446..511）写回 |
| `syslinux --install` 报 "This program needs root privilege" | syslinux 6.03 的 Linux 安装器在 euid≠0 时直接退出；它是 32 位二进制，`fakeroot` 的 LD_PRELOAD 也不适用 | 改用 GRUB 路径；免 root 造盘不再需要 syslinux |
| `vga=791` 无效，内核提示 "Unknown kernel command line parameters" | 现代内核已把 `vga=` 移出内核参数（透传给用户空间） | 由 GRUB 用 `gfxpayload=1024x768x16` 设 VBE 模式并通过 `screen_info` 传给内核 |
| `root=LABEL=root` 挂不上（`unknown-block(0,0)`），换成 `root=/dev/sda2` 就好 | 该场景下按标签解析未成功（设备已识别，`sda` 正常出现） | 镜像内固定 `root=/dev/sda2`（单盘机确定；多盘机器应改回 LABEL 并排查解析） |
| 内存扫描全档报 no，QEMU 日志 "Failed to get write lock" | `pgrep -x qemu-system-x86_64` 匹配不到——内核把 comm 截断为 15 字符（`qemu-system-x86`），上一档 QEMU 未被杀掉、占着镜像写锁 | 改为遍历 `/proc/*/cmdline` 匹配镜像路径 |

### 6.4 apk 相关（供 M2 写仓库脚本时参考）

| 症状 | 原因 | 修法 |
|---|---|---|
| `mkpkg` 报 `required info field 'name' not provided` | **`--compat` 是带参数选项**，写成裸 `--compat` 会吞掉紧随其后的 `-I`，导致 info 全没传进去 | 不传 `--compat`（默认值已可用）；此处一度被误判为上游 bug，实为调用方错误 |
| `apk index` 报 `file format not supported (in this applet)` | apk-tools 3.x 产出的是 **v3（ADB）格式**包，`apk index` 只处理 v2 | 用 `apk mkndx` 建索引（同样需要 `--allow-untrusted`） |
| 从发行版仓库装包失败于依赖 | 第三方包的依赖几乎都包含 `so:libc.musl-x86_64.so.1`，而本系统是全静态、且 apk 数据库里没有该提供者 | 若要让 apk 吃第三方包，需**把 musl 作为共享库打包并把基础依赖注册进 apk 数据库**——这是 M2/M3 的设计项，不是单点修补 |

## 7. 上真机（X61）

```sh
# 在任意 Linux 上写入（会清空目标盘，务必确认设备名）
sudo dd if=build/amd64/constellation-x61.img of=/dev/sdX bs=4M status=progress conv=fsync
```

- **BIOS**：SATA 保持 **AHCI** 模式（`CONFIG_SATA_AHCI` 已内置）；引导为传统
  BIOS，不需要 UEFI（GRUB i386-pc）。
- **登录**：`root` + 构建时 `ROOT_PASSWORD_HASH` 对应的密码。
- **网络**：有线口（82566MM）由 udhcpc 自动取地址。
- **显示**：GRUB 用 `gfxpayload` 设 VBE 模式（默认 `1024x768x16`，可用环境变量
  `GFXPAYLOAD` 覆盖），X3100 上应得到对应分辨率的 16bpp 帧缓冲控制台。
  16bpp 只需 1.5 MB 显存（1400x1050 时 2.8 MB），符合低内存取向。
  若某台 BIOS 的 VBE 不接受该模式导致黑屏，删掉 `set gfxpayload` 一行即可退回
  80x25 文本控制台。
  - 高分屏实测：`GFXPAYLOAD=1400x1050x16` 在本配置下可正常起来
    （`vesafb: mode is 1400x1050x16, linelength=2800`，`/proc/fb` → `1400,1050`，
    16bpp，显存占用 2880 KB）。这证明**机制**可用，真机是否能拿到该模式取决于
    X61 BIOS 的 VBE 模式表（面板原生 1400x1050 的机器通常提供；可在 GRUB 命令行
    用 `videoinfo` 列出实际可用模式）。
- **镜像只占 512 MiB**：90GB SSD 的其余空间未使用。要扩容用 `parted` 调整 p2
  再 `resize2fs`（需 root）。
- **不在范围内**：无线（3945/4965 需固件与驱动，本风味未编）、音频、挂起/恢复、
  SSD TRIM。这些与设计文档中"非首发起"的取舍一致。

## 8. 未完成 / 边界

- **未在真机验证**：以上全部结论来自 QEMU（q35 + ich9-ahci + e1000e）。
  ICH8M、82566MM、X3100 在真机上的实际行为需在 X61 上确认。
- **apk 生态**：目前只有自建示例仓库（`constellation-release`）。真正的
  ~30 包基础仓库是 M2 的开放项；其中"共享 libc + 基础依赖入库"是前置设计。
- **内存压缩**：zram(lz4) 已启用并有 16 MiB 交换区，但"重度 swap 下的交互
  可用性"（设计文档 D7 关心的问题）尚未做主观评估。

## 9. 图形路线的边界：i3 与 tinywm 各自的位置

结论：**i3wm 与项目的命题直接冲突，不在任何现有档位内**；而 vendored 的
tinywm 虽然自己够小，却卡在 X server 上，而不是卡在 WM 上。

### 9.1 i3 为什么没有位置

i3 的依赖链决定了它不是"一个 WM"，而是一整套桌面工具链：

- 直接依赖：xcb 系列（xcb-util / -wm / -keysyms / -cursor / -xrm）、
  libxkbcommon、**cairo**、**pango**、libev、yajl、startup-notification；
- 其中 cairo/pango 又会拉进 freetype、fontconfig、harfbuzz、libpng 等。

内存量级：完整 Xorg 常驻约 30–50 MB，i3 + cairo/pango 约 15–25 MB，
合计一个可用会话约 **100–160 MB**（还没算终端与启动器）。对照本项目的分档
（T0 24 / T1 40 / T2 64 MiB），i3 落在 T2 锚点之外约 2–3 倍。

更根本的是：**cairo/pango 正是项目命题所针对的那类"选型"**。设计文档的论点是
"高内存地板来自选型而非上游版本"，i3 恰好是靠现代图形栈换来的功能——收下它
就等于放弃那条论点，而不是"优化一下就能塞进去"。

另外当前风味 `CONFIG_DRM=n`（只有 vesafb，无 KMS）。要跑任何真实 X 会话，
先得把显示路线换成 i915 DRM/KMS（Gen4 支持 X3100，还能顺带拿到面板原生分辨率）。

### 9.2 tinywm 的位置

tinywm 确实是唯一可能塞进 T1 的 WM 路线：`tinywm.c` 51 行，仅依赖 libX11
（不含 cairo/pango），常驻远低于 1 MB。

但**瓶颈不在它**：tinywm 需要一个 X server，而主流的小体积 X server
（kdrive/TinyX，Xfbdev）已在 xorg-server 21.1 被移除（设计文档 §3.3 已记）。
完整 Xorg 会直接顶穿 T1 预算。所以真正的前置问题是"用哪个 X server"：

| X server 路线 | 代价 |
|---|---|
| 自维护 xorg-server 21.0 的 kdrive | 唯一能配 tinywm 守住 T1 的路线，但要背一个已死分支 |
| 完整 Xorg（+ fbdev 或 i915 modesetting） | 直接进入 100 MB 以上，等于放弃 T0/T1 |
| 不做 WM，走 fb 直连（fbi / links2 -g） | **设计文档已选的路**，无 WM 开销 |

若确定要做，把 tinywm 改到"能用"大致需要（Xlib，无 cairo/pango 可用）：

- 键盘驱动（`XGrabKey`）：提降、关闭、焦点循环；
- 焦点策略与窗口列表；
- 装饰：要么不做（平铺），要么只能用 Xlib 核心字体画标题；
- EWMH 的最小子集，否则现代程序行为异常；

量级约 300–800 行 C。一句话：**先定 X server，再谈 WM**——顺序反了会白写。
